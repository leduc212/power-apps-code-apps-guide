# Chapter 11: Building with an AI Coding Agent

> **Blog post title:** Building a Power Apps Code App with an AI Coding Agent: Rules, Specs and Review
>
> **Audience:** You're going to build or migrate a Code App with Claude Code, GitHub Copilot or another coding agent, and you want the result to be something you'd put in front of users.
>
> **Part 2** is based on a production Code App we implemented to replace a large Canvas App. The patterns are real; the examples are rewritten against this repo's demo.

---

## Introduction

We built our production Code App with an AI coding agent (Claude Code) doing most of the typing. A person set the direction, confirmed every spec, ran every sign-in and deploy, and checked every screen against the Canvas app.

At GA I wrote that AI agents might be Code Apps' killer feature, because Power Fx and a drag-and-drop canvas are hard for agents and TypeScript and React are what they're best at. After a real project, I'd keep that and add the part I hadn't learned yet: **an agent is wrong in specific, predictable ways, and most of the work is setting things up so those ways get caught.**

This chapter covers the setup that worked:

1. **Microsoft's code apps plugin** for the generic parts
2. **A project rules file**, where every rule is a mistake that happened once
3. **Specs before code**
4. **Human gates** for anything that touches an environment
5. **Review** aimed at where agent bugs actually are
6. **Memory across sessions**, kept in the repo

The demo has a worked example of the rules file: [`crm-sales-hub/AGENTS.md`](../crm-sales-hub/AGENTS.md). There's a template for migration projects in [`templates/agent/AGENTS.md`](../templates/agent/AGENTS.md).

## 1. Microsoft's Code Apps Plugin

Microsoft publishes a plugin for coding agents in the [power-platform-skills](https://github.com/microsoft/power-platform-skills) marketplace. It works with GitHub Copilot CLI and Claude Code:

```
/plugin marketplace add microsoft/power-platform-skills
/plugin install code-apps-preview@power-platform-skills
```

It adds skills for creating an app, adding data sources (Dataverse, SharePoint, Teams, Office 365, OneDrive, Azure DevOps, Copilot Studio agents, or any other connector), listing connections and deploying. It runs the `pa` CLI for you, and checks and installs prerequisites the first time. Microsoft's [Copilot quickstart](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/quickstart-github-copilot) goes from a paragraph of description to a deployed app.

Use it for what it's good at: scaffolding, adding data sources, and the mechanics of the CLI. Its guidance also states the rule that belongs at the top of every Code App project:

> **No direct HTTP.** Code Apps run in a sandbox where `fetch`, `axios` and Graph calls don't work at runtime. All external data goes through Power Platform connectors.

What the plugin can't know is **your** project: which tables are yours, what the old app did, what "done" means, what your users expect, and which mistakes this particular codebase invites. That's the rules file.

## 2. A Project Rules File

Most coding agents read a rules file at the root of the repository: `AGENTS.md` for most, `CLAUDE.md` for Claude Code. The demo keeps its rules in `AGENTS.md`, and its `CLAUDE.md` is a single line that imports it:

```
@AGENTS.md
```

The demo's file is short: hard rules, what the human does, what "done" means, and where things are. Our production file was the same shape, plus a status section at the top (section 6) and a table of where each kind of truth lives.

### Every rule is a mistake

The useful rules are each a mistake: a few anticipated on day one because the library was young, most added the day the agent actually made them.

| The mistake | The rule it became |
|---|---|
| Calling an SDK method that doesn't exist. The library is young, and an agent fills the gaps from other libraries' conventions | **Check every call against the generated service.** If it isn't in `src/generated/services/`, it doesn't exist |
| "Fixing" a type error by editing a generated model | **Never edit `src/generated/`.** Schema changes are regenerated by the human, and the agent reviews the diff |
| `getAll()` with no `select` and no paging on a large table | **Every query sets `select`; lists use the paging hook** |
| Reporting confidently that some data "isn't stored anywhere", and proposing new columns and changes to several flows | **A sources-of-truth table** (below) |
| Screens built with plain default grids and label/value lists | **UI expectations written down**: cards for detail sections, full-width tables, sorting in the header |
| Typographic dashes in UI text where the team wanted plain hyphens | **UI text conventions**, in one line |

The "isn't stored anywhere" case is the one worth studying. The agent looked in `src/generated/` and `power.config.json`, found no table holding the data, and concluded it didn't exist. But those files list only the tables *this app had onboarded*, not what exists in Dataverse. The table had existed all along, written by several flows. The fix was one `pa app add data-source`, not a week of platform work. The agent's reasoning was fine; its sources were wrong.

So the rules file says where each kind of truth lives:

| Question | Answer lives in | Not in |
|---|---|---|
| What did the Canvas app do? | The pinned solution export (screens and flow definitions) | Memory, or the generated files |
| Does a table or column exist? | The solution export's metadata and the flows' write actions | `src/generated/` |
| What should this screen do? | The confirmed spec | The YAML alone |
| Is this difference intentional? | The differences log | |

### Keep it short and current

An agent follows the rules file literally, **including the parts that are out of date.** Ours still told every new session to "delete and re-add" a data source after a schema change, long after we'd found that re-adding alone refreshed it (and that the delete command crashed on one machine). Prune the file like code. When a rule stops being true, delete it the same day.

## 3. Specs Before Code

For every screen, and every slice of a large one, the agent wrote a spec first (Chapter 10, [`SCREEN_SPEC.md`](../templates/migration/SCREEN_SPEC.md)): data, state, every control's behaviour, the business rules exactly, a parity checklist and open questions. Then it stopped, and a person confirmed it.

This is where an agent is strongest. Reading a 10,000-line YAML file and listing *everything* it does is tedious for a person and routine for an agent. It doesn't get bored at line 6,000, and it doesn't skip the `DisplayMode` on the fourth button.

The spec also changes what review means. Without one, reviewing agent code means reverse-engineering what it was *supposed* to do. With one, you check the code against a list you've already agreed. And the **open questions** section is where the agent says what it couldn't decide from the YAML. That list is worth more than any of the code.

## 4. Human Gates

Some things the agent never did, by rule:

- **Sign-ins.** `pa auth login`, `pa app init`: anything that opens a browser. These are interactive, and they decide which tenant everything else touches.
- **Anything that changes an environment.** Adding or refreshing data sources, pushing, sharing, and all changes in Dataverse or Power Automate.
- **Deploying.** The agent finishes by saying what changed and that it is **not deployed**. "It builds" isn't "it's live", and an agent that blurs the two will eventually tell someone a fix is out when it isn't.

Many tasks had a platform half (a new column, a flow change) and an app half. For those, **the plan went into the repo as a document**, not just into the chat: the human's steps (detailed enough to follow in the maker portal without the agent) separated from the agent's steps, marked as waiting. The human did the platform work on their own schedule, then said "go". A plan in a chat window disappears with the session; a plan in `docs/specs/` is still there when the platform work is finished three days later.

## 5. Review Where the Bugs Are

Agent code is fluent. It compiles, it's consistently formatted, and it reads as if it were right. That's exactly why it needs review aimed at specific places. In our project, the bugs that reached review clustered in a few:

**Error paths.** The happy path is almost always right. The bug from Chapter 8, where an unreadable flow response was recorded as a success, sat in code with a comment saying the failure "falls through to the error check". The check was inside a block that never ran for that case. The comment described the intent; the code did something else. **Read error branches against their comments.**

**Where the types lie.** The generated types say `string` where Dataverse sends a number (Chapter 3). An agent trusts the types. Look at every comparison and every write payload on choice and money columns.

**Queries inside loops.** A `LookUp` in a Canvas gallery translates naturally into a query per row (Chapter 7). Look for `await` inside `for` and `.map`.

**Silent limits.** `top` on a list, `getAll()` without paging, a filter applied in the browser to a partial list. None of these fail; they're just wrong on real data volumes.

**Strings built from input.** Filters built with template strings and no escaping.

**The flow's side.** When code calls a flow, check what the flow returns and what the old screen did afterwards (Chapter 10, "What Canvas hid").

**Ask the agent what it couldn't verify.** Every task ended with a list: what was built, what was checked (build, lint, tests), and what couldn't be checked without a person (anything needing sign-in, live data, or the Canvas app). An agent that says "done" with no such list is guessing, and so are you.

## 6. Memory Across Sessions

Every agent session starts cold. Across a project that runs for weeks, the question is where continuity lives.

**In the repo.** Ours had:

- **A status section at the top of the rules file**: "where we are, what to read next". Updated at the end of every session, and the first thing a new session reads.
- **The migration tracker**: every screen's spec, build, parity and test status.
- **The specs**: what each screen must do, as agreed.
- **The differences log**: every decision already made, so it isn't made differently next week.

These documents are the agent's long-term memory, and the team's. Some agents also keep their own notes between sessions, which help with preferences and working habits. Our rules file said plainly that **the repo documents win** when the two disagree. An agent's private notes can't be reviewed in a pull request; a tracker can.

## 7. What Changed in How We Worked

With an agent writing most of the code, the bottleneck moved. Code was rarely what we were waiting for. We waited for:

- **Specs to be confirmed** by someone who knew how the Canvas app was really used
- **Parity checks** against the live app (Chapter 10)
- **Platform changes** that only a person with the right access could make
- **Review**, the part no one can skip

Plan for that. The estimate that matters isn't how long the code takes; it's how many hours a week the people who know the app can give to confirming, checking and reviewing it.

> The September update of this guide was made the same way. An agent audited every claim in the February version against the SDK source, Microsoft's docs and the production project, and wrote the corrections. Anything it couldn't verify against a live environment is marked as such in the chapters and in [`docs/v2-audit.md`](../docs/v2-audit.md). The human decided what to keep, what to publish, and what stays confidential.

## Key Takeaways

- Code Apps suit AI coding agents, but an agent is wrong in predictable ways; the work is catching them
- Use **Microsoft's code apps plugin** for scaffolding, connectors and the CLI; remember its first rule, **no direct HTTP**
- Keep a short **`AGENTS.md`** (and a `CLAUDE.md` that imports it). Add a rule each time the agent makes a new kind of mistake, and delete rules the day they stop being true
- Tell the agent **where truth lives**: `src/generated/` lists what the app onboarded, not what exists
- **Specs before code**: the agent extracts, a person confirms, and the spec becomes the review checklist
- **Humans own sign-ins, environments and deploys**; platform plans go into the repo, with the human's steps separated
- **Review error paths, type assumptions, loops, silent limits and flow contracts**, and always ask what couldn't be verified
- **Continuity lives in the repo**: status, tracker, specs, differences log
- With an agent, confirming, checking and reviewing become the bottleneck; plan people's time, not typing time
